PSI • LEKCJA 39 • TESTOWANIE I WALIDACJA

Testowanie witryn w różnych przeglądarkach i rozdzielczościach. Walidacja HTML i CSS

Cel lekcji: poznanie metod testowania stron internetowych, sprawdzania responsywności i zgodności z przeglądarkami oraz wykrywania i poprawiania błędów HTML i CSS za pomocą narzędzi deweloperskich i walidatorów W3C.

Czas realizacji: 2 × 45 minut.

1. Wprowadzenie

Po zakończeniu tworzenia strony internetowej nie wystarczy sprawdzić, czy otwiera się ona na komputerze autora.

Użytkownicy korzystają z różnych urządzeń, przeglądarek i rozmiarów ekranów. Witryna może wyglądać prawidłowo na dużym monitorze, ale mieć problemy z wyświetlaniem na telefonie.

Mogą również występować błędy w kodzie, niedziałające odnośniki, niewczytujące się obrazy lub formularze, których nie można obsłużyć.

Dlaczego testujemy strony?

  • Aby wykryć błędy przed publikacją.
  • Aby sprawdzić działanie witryny w różnych przeglądarkach.
  • Aby zapewnić poprawny wygląd na różnych ekranach.
  • Aby sprawdzić poprawność kodu HTML i CSS.
  • Aby poprawić dostępność i wygodę użytkowania.
  • Aby uniknąć problemów z działaniem strony.

📌 Zapamiętaj

Testowanie witryny to proces sprawdzania, czy strona działa poprawnie w różnych warunkach i spełnia określone wymagania.

2. Rodzaje testów stron internetowych

Testowanie witryn obejmuje kilka obszarów. Każdy z nich pozwala wykryć inny rodzaj problemów.

Rodzaj testu Co sprawdzamy?
Funkcjonalny Czy odnośniki, formularze i przyciski działają poprawnie?
Responsywności Czy układ dostosowuje się do różnych szerokości ekranu?
Międzyprzeglądarkowy Czy strona działa w różnych przeglądarkach?
Walidacja HTML Czy kod HTML jest zgodny z regułami języka?
Walidacja CSS Czy deklaracje i składnia CSS są poprawne?
Dostępności Czy strona jest możliwa do obsługi przez osoby o różnych potrzebach?
Wydajności Czy strona wczytuje się sprawnie i nie przesyła zbędnych danych?

Dobrze przetestowana witryna powinna przejść więcej niż jeden rodzaj testów.

3. Testowanie w różnych przeglądarkach

Przeglądarka internetowa interpretuje kod HTML, CSS i JavaScript, a następnie wyświetla stronę użytkownikowi.

Popularne przeglądarki

  • Google Chrome
  • Mozilla Firefox
  • Microsoft Edge
  • Safari
  • Opera

Dlaczego wygląd może się różnić?

Przeglądarki mogą wykorzystywać różne silniki renderujące, a także różnić się obsługą wybranych funkcji i ustawieniami domyślnymi.

Chrome i Edge korzystają z silnika Blink, Firefox z Gecko, a Safari z WebKit.

Co należy sprawdzić?

  1. Czy strona otwiera się poprawnie?
  2. Czy tekst jest czytelny?
  3. Czy wszystkie obrazy się wyświetlają?
  4. Czy menu działa?
  5. Czy układ elementów jest poprawny?
  6. Czy przyciski reagują prawidłowo?
  7. Czy formularze można obsługiwać?

⚠️ Ważne

Sprawdzenie strony tylko w Chrome nie jest pełnym testem międzyprzeglądarkowym. W miarę możliwości należy użyć co najmniej dwóch przeglądarek z różnymi silnikami.

4. Zgodność międzyprzeglądarkowa

Zgodność międzyprzeglądarkowa oznacza, że strona zachowuje poprawną funkcjonalność i czytelność w obsługiwanych przeglądarkach.

Nie oznacza to, że każdy element musi wyglądać idealnie identycznie.

Przykład

Formularz może mieć nieco inny wygląd pola wyboru w Chrome i Firefox, ale powinien umożliwiać wykonanie tych samych działań.

Co może powodować problemy?

  • Nieobsługiwane właściwości CSS.
  • Błędna składnia HTML.
  • Różnice w stylach domyślnych.
  • Nieprawidłowe ścieżki do plików.
  • Błędy skryptów JavaScript.
  • Nieprawidłowe założenia dotyczące rozmiaru ekranu.

Sprawdzanie obsługi właściwości

W razie wątpliwości można skorzystać z serwisu:

Can I Use – zgodność technologii internetowych

Serwis pozwala sprawdzić, które przeglądarki obsługują wybrane funkcje HTML, CSS i JavaScript.

5. Rozdzielczość ekranu a viewport

Rozdzielczość ekranu określa liczbę pikseli tworzących obraz na urządzeniu.

Podczas projektowania responsywnego szczególnie ważny jest jednak viewport, czyli obszar, w którym przeglądarka wyświetla stronę.

Przykładowe szerokości testowe

Urządzenie Przykładowa szerokość viewportu
Mały telefon 320 px
Telefon 375 px
Większy telefon 430 px
Tablet 768 px
Laptop 1366 px
Duży monitor 1920 px

Są to przykładowe wartości testowe, a nie sztywne granice poszczególnych typów urządzeń.

Znacznik viewport

<meta name="viewport"
      content="width=device-width, initial-scale=1.0">

Znacznik ten informuje przeglądarkę mobilną, jak ustawić szerokość obszaru wyświetlania strony.

📌 Zapamiętaj

Podczas testowania responsywności sprawdzamy przede wszystkim szerokość viewportu, a nie tylko fizyczną rozdzielczość ekranu.

6. Narzędzia deweloperskie przeglądarki

Nowoczesne przeglądarki posiadają narzędzia deweloperskie, które pomagają analizować kod i wygląd witryny.

Otwieranie DevTools

W Chrome i Edge na Windows można użyć klawisza: 

F12

Można również kliknąć prawym przyciskiem myszy wybrany element strony i wybrać Zbadaj.

Najważniejsze zakładki

Zakładka Zastosowanie
Elements / Elementy Analiza struktury HTML i zastosowanych stylów CSS.
Console / Konsola Wyświetlanie komunikatów i błędów JavaScript.
Network / Sieć Sprawdzanie pobieranych plików i odpowiedzi serwera.
Device Toolbar Symulowanie różnych szerokości viewportu.

Co można sprawdzić w zakładce Elements?

  • Strukturę elementów HTML.
  • Przypisane klasy CSS.
  • Wymiary elementów.
  • Marginesy i odstępy wewnętrzne.
  • Kolory i rozmiary tekstu.
  • Reguły CSS wpływające na wygląd elementu.

7. Testowanie responsywności strony

Responsywna witryna powinna dostosowywać układ do dostępnej szerokości ekranu.

Instrukcja w Chrome lub Edge

  1. Otwórz stronę internetową.
  2. Naciśnij F12.
  3. Włącz tryb urządzeń za pomocą ikony telefonu i tabletu.
  4. Wybierz tryb Responsive.
  5. Ustaw szerokość 375 px.
  6. Sprawdź wygląd strony.
  7. Zmień szerokość na 768 px.
  8. Następnie sprawdź 1366 px.

Na co zwrócić uwagę?

  • Czy tekst mieści się w ekranie?
  • Czy nie pojawia się niepotrzebne przewijanie poziome?
  • Czy obrazy nie wychodzą poza kontener?
  • Czy menu jest czytelne?
  • Czy przyciski można wygodnie nacisnąć?
  • Czy kolumny zmieniają układ?
  • Czy formularze mieszczą się na ekranie?

Przykładowe media queries

.karty {
    display: flex;
    gap: 20px;
}

.karta {
    flex: 1;
}

@media (max-width: 768px) {
    .karty {
        flex-direction: column;
    }
}

Przy szerokości większej niż 768 px karty są rozmieszczone w rzędzie. Przy szerokości 768 px lub mniejszej ustawiają się jedna pod drugą.

⚠️ Ważne

Tryb urządzeń w DevTools jest przydatną symulacją, ale nie zastępuje całkowicie testowania na prawdziwym telefonie lub tablecie.

8. Testowanie funkcjonalności witryny

Test funkcjonalny sprawdza, czy elementy interaktywne działają zgodnie z przeznaczeniem.

Przykładowa lista kontrolna

Element Co sprawdzić?
Odnośniki Czy prowadzą do właściwych stron?
Menu Czy wszystkie pozycje działają?
Formularze Czy pola można wypełniać i czy działa walidacja?
Przyciski Czy wykonują oczekiwane działania?
Obrazy Czy są poprawnie wczytywane?
Nawigacja klawiaturą Czy można przechodzić między elementami za pomocą Tab?

Przykład testowania formularza

  1. Spróbuj wysłać pusty formularz.
  2. Sprawdź, czy wymagane pola są kontrolowane.
  3. Wprowadź niepoprawny adres e-mail.
  4. Sprawdź reakcję formularza.
  5. Wprowadź poprawne dane testowe.
  6. Sprawdź, czy formularz zachowuje się zgodnie z projektem.

Jeżeli formularz nie ma obsługi wysyłania danych, sprawdzamy jedynie funkcje, które rzeczywiście zostały zaimplementowane.

9. Czym jest walidacja kodu?

Walidacja polega na sprawdzaniu kodu według reguł określonego języka lub standardu.

Walidator analizuje kod i informuje o wykrytych błędach oraz ostrzeżeniach.

Dlaczego warto walidować kod?

  • Pomaga wykrywać błędy składni.
  • Ułatwia utrzymanie poprawnej struktury dokumentu.
  • Pomaga znaleźć niepoprawne atrybuty.
  • Ułatwia analizę problemów z wyświetlaniem strony.
  • Wspiera tworzenie kodu zgodnego ze specyfikacjami.

Walidacja a testowanie

Walidacja nie jest tym samym co pełne testowanie witryny.

Strona może przejść walidację, ale nadal mieć niedziałające odnośniki, nieczytelny tekst lub problemy z obsługą klawiaturą.

📌 Zapamiętaj

Poprawna walidacja kodu nie gwarantuje poprawnego działania całej witryny.

10. Walidacja kodu HTML

Do sprawdzania dokumentów HTML można wykorzystać oficjalne narzędzie:

Nu Html Checker – walidator HTML

Metody sprawdzania kodu

  • Podanie adresu URL publicznej strony.
  • Przesłanie pliku HTML.
  • Wklejenie kodu HTML do formularza.

Instrukcja krok po kroku

  1. Otwórz walidator HTML.
  2. Wybierz metodę sprawdzania kodu.
  3. Prześlij plik index.html lub wklej jego zawartość.
  4. Uruchom sprawdzanie.
  5. Przeczytaj komunikaty walidatora.
  6. Odszukaj wskazane fragmenty kodu.
  7. Popraw błędy.
  8. Uruchom walidację ponownie.

Rodzaje komunikatów

Komunikat Znaczenie
Error Wykryto błąd wymagający analizy i poprawy.
Warning Ostrzeżenie dotyczące potencjalnego problemu.
Info Informacja pomocnicza.

⚠️ Ważne

Adres localhost nie jest publicznie dostępny dla walidatora internetowego.

W przypadku strony lokalnej użyj opcji przesłania pliku lub wklejenia kodu.

11. Typowe błędy HTML

Błąd 1 – Brak zamknięcia elementu

Niepoprawnie:

<p>Witamy na stronie
<p>To kolejny akapit.</p>

W HTML niektóre znaczniki końcowe mogą być pomijane zgodnie z regułami języka. Jednak dla początkujących bezpieczniej jest zapisywać wyraźne zamknięcia akapitów.

Czytelniejszy zapis:

<p>Witamy na stronie.</p>
<p>To kolejny akapit.</p>

Błąd 2 – Nieprawidłowe zagnieżdżenie

Niepoprawnie:

<p>
    <strong>Ważny tekst
</p>
    </strong>

Poprawnie:

<p>
    <strong>Ważny tekst</strong>
</p>

Błąd 3 – Brak tekstu alternatywnego

Niepoprawnie:

<img src="szkola.jpg">

Poprawnie:

<img src="szkola.jpg"
     alt="Budynek szkoły widziany od frontu">

Obraz czysto dekoracyjny może mieć pusty atrybut alt="".

Błąd 4 – Powtarzające się identyfikatory

Niepoprawnie:

<section id="kontakt">
    <h2>Kontakt</h2>
</section>

<section id="kontakt">
    <h2>Adres</h2>
</section>

Poprawnie:

<section id="kontakt">
    <h2>Kontakt</h2>
</section>

<section id="adres">
    <h2>Adres</h2>
</section>

Błąd 5 – Niepoprawne zagnieżdżenie elementów

Niepoprawnie:

<ul>
    <p>Pierwszy punkt</p>
    <p>Drugi punkt</p>
</ul>

Poprawnie:

<ul>
    <li>Pierwszy punkt</li>
    <li>Drugi punkt</li>
</ul>

12. Walidacja kodu CSS

Arkusze stylów CSS również można sprawdzać za pomocą walidatora.

W3C CSS Validation Service

Co sprawdza walidator CSS?

  • Składnię reguł CSS.
  • Poprawność nazw właściwości.
  • Poprawność wartości deklaracji.
  • Wybrane błędy zapisu arkusza.

Instrukcja krok po kroku

  1. Otwórz walidator CSS.
  2. Wybierz sprawdzanie przez przesłanie pliku lub wklejenie kodu.
  3. Wskaż plik style.css.
  4. Uruchom walidację.
  5. Przeczytaj komunikaty.
  6. Popraw wykryte błędy.
  7. Sprawdź arkusz ponownie.

Przykład poprawnej reguły CSS

h1 {
    color: #1E3A8A;
    font-size: 32px;
    text-align: center;
}

W CSS każda deklaracja zawiera nazwę właściwości, dwukropek i wartość.

📌 Zapamiętaj

Walidator CSS pomaga wykrywać błędy składni, ale nie ocenia, czy zaprojektowany wygląd strony jest estetyczny i czytelny.

13. Typowe błędy CSS

Błąd 1 – Niepoprawna nazwa właściwości

Niepoprawnie:

h1 {
    colour: red;
}

Poprawnie:

h1 {
    color: red;
}

Błąd 2 – Brak jednostki

Niepoprawnie:

p {
    font-size: 20;
}

Poprawnie:

p {
    font-size: 20px;
}

Błąd 3 – Niepoprawna wartość

Niepoprawnie:

.karta {
    display: flexbox;
}

Poprawnie:

.karta {
    display: flex;
}

Błąd 4 – Brak nawiasu klamrowego

Niepoprawnie:

.box {
    background-color: #DBEAFE;
    padding: 20px;

Poprawnie:

.box {
    background-color: #DBEAFE;
    padding: 20px;
}

Błąd 5 – Brak średnika między deklaracjami

Niepoprawnie:

p {
    color: blue
    font-size: 18px;
}

Poprawnie:

p {
    color: blue;
    font-size: 18px;
}

⚠️ Ważne

Średnik po ostatniej deklaracji w bloku CSS nie zawsze jest wymagany, ale warto go stosować dla czytelności i łatwiejszej edycji.

14. Konsola przeglądarki i błędy zasobów

Nie wszystkie problemy zostaną wykryte przez walidatory HTML i CSS.

Warto również korzystać z konsoli przeglądarki i zakładki Network.

Przykład błędu 404

Failed to load resource:
the server responded with a status of 404

Komunikat może oznaczać, że przeglądarka próbowała pobrać plik, którego nie znaleziono pod wskazanym adresem.

Przykład niepoprawnej ścieżki

<img src="images/logo.png"
     alt="Logo strony">

Jeżeli plik znajduje się w folderze img, ścieżka jest błędna.

Poprawna ścieżka

<img src="img/logo.png"
     alt="Logo strony">

Co sprawdzać w konsoli?

  • Błędy JavaScript.
  • Nieudane próby pobierania zasobów.
  • Komunikaty ostrzegawcze.
  • Informacje pomocne w diagnozowaniu problemów.

15. Podstawowe testowanie dostępności

Dostępność stron internetowych oznacza projektowanie witryn z uwzględnieniem różnych potrzeb użytkowników.

Podczas testowania warto odwołać się do zasad WCAG poznanych na wcześniejszej lekcji.

Przykładowe testy dostępności

  1. Sprawdź, czy obrazy informacyjne mają opisy alternatywne.
  2. Sprawdź czytelność tekstu i kontrast.
  3. Spróbuj obsługiwać stronę samą klawiaturą.
  4. Sprawdź, czy fokus jest widoczny.
  5. Sprawdź, czy formularze mają etykiety.
  6. Powiększ stronę do 200% i sprawdź jej czytelność.
  7. Sprawdź, czy nagłówki tworzą logiczną strukturę.

Test klawiaturą

Naciśnij klawisz Tab i obserwuj, czy możesz przechodzić między odnośnikami i przyciskami.

Użyj Enter, aby uruchomić wybrany odnośnik.

📌 Zapamiętaj

Walidacja HTML i CSS nie zastępuje testowania dostępności.

16. Podstawowe testowanie wydajności

Wydajność witryny wpływa na komfort użytkowników. Strona zawierająca bardzo duże obrazy może wczytywać się wolniej.

Co wpływa na szybkość działania?

  • Rozmiar obrazów.
  • Liczba pobieranych plików.
  • Wielkość arkuszy CSS i skryptów.
  • Wydajność serwera.
  • Jakość połączenia internetowego.
  • Sposób wczytywania zasobów.

Przydatne narzędzie

PageSpeed Insights

Narzędzie pozwala analizować wydajność publicznie dostępnych stron.

Do sprawdzania lokalnych stron można wykorzystać również narzędzia deweloperskie, w tym Lighthouse, jeśli jest dostępny w przeglądarce.

⚠️ Uwaga

PageSpeed Insights nie przeanalizuje zwykłej lokalnej strony dostępnej wyłącznie pod adresem localhost.

17. Scenariusze testowe

Scenariusz testowy opisuje, co należy sprawdzić i jaki wynik jest oczekiwany.

Przykład scenariusza

Element Opis
Test Sprawdzenie menu na telefonie.
Warunki Viewport o szerokości 375 px.
Działanie Otworzenie strony i kliknięcie pozycji Kontakt.
Oczekiwany wynik Przejście do właściwej sekcji lub podstrony.

Przykładowe scenariusze

  1. Sprawdzenie wyglądu strony przy 375 px.
  2. Sprawdzenie układu kart przy 768 px.
  3. Sprawdzenie menu przy 1366 px.
  4. Sprawdzenie działania wszystkich odnośników.
  5. Sprawdzenie poprawności kodu HTML.
  6. Sprawdzenie poprawności kodu CSS.

18. Raportowanie wykrytych błędów

Po zakończeniu testowania należy zapisać wyniki.

Raport pomaga ustalić, które elementy wymagają poprawy.

Przykładowy raport

Nr Problem Warunki Status
1 Obraz wychodzi poza ekran. 375 px Do poprawy
2 Nie działa odnośnik Kontakt. Firefox Do poprawy
3 Brak atrybutu alt. Walidator HTML Do poprawy
4 Niepoprawna wartość display. Walidator CSS Poprawiono

Dobry opis błędu zawiera:

  • nazwę problemu,
  • miejsce jego występowania,
  • warunki testowania,
  • oczekiwany wynik,
  • rzeczywisty wynik,
  • status poprawki.

19. Poprawianie błędów i ponowne testowanie

Wykrycie błędu to dopiero pierwszy etap pracy. Należy jeszcze usunąć jego przyczynę i sprawdzić, czy poprawka działa.

Przykład – obraz wychodzi poza ekran

Problem:

img {
    width: 900px;
}

Obraz ma stałą szerokość, która może przekraczać szerokość ekranu telefonu.

Poprawka:

img {
    max-width: 100%;
    height: auto;
}

Przykład – sztywny kontener

Problem:

.container {
    width: 1200px;
}

Poprawka:

.container {
    width: 90%;
    max-width: 1200px;
    margin: 0 auto;
}

Cykl poprawiania

  1. Wykryj błąd.
  2. Ustal jego przyczynę.
  3. Popraw kod.
  4. Zapisz pliki.
  5. Odśwież stronę.
  6. Powtórz test.
  7. Sprawdź, czy poprawka nie spowodowała nowego problemu.

20. Przykład kompleksowego testowania witryny

Załóżmy, że przygotowaliśmy stronę „Moje zainteresowania”.

Witryna zawiera nagłówek, menu, trzy karty z obrazami, formularz kontaktowy i stopkę.

Plan testowania

Etap Działanie
1 Otwórz stronę w Chrome.
2 Sprawdź ją w Firefox lub Edge.
3 Przetestuj szerokości 375, 768 i 1366 px.
4 Sprawdź działanie menu i formularza.
5 Przeprowadź walidację HTML.
6 Przeprowadź walidację CSS.
7 Sprawdź konsolę i pobieranie zasobów.
8 Popraw wykryte błędy.
9 Powtórz testy.

📌 Wniosek

Poprawnie przygotowana witryna powinna być sprawdzona zarówno automatycznymi narzędziami, jak i przez samodzielne wykonanie testów funkcjonalnych.

📌 Zapamiętaj

  • Testowanie pozwala wykrywać problemy przed publikacją strony.
  • Witrynę należy sprawdzać w różnych przeglądarkach.
  • Zgodność międzyprzeglądarkowa nie wymaga identycznego wyglądu każdego elementu.
  • Viewport to obszar wyświetlania strony w przeglądarce.
  • Responsywność należy sprawdzać przy różnych szerokościach viewportu.
  • DevTools umożliwia analizowanie HTML, CSS i działania strony.
  • F12 otwiera narzędzia deweloperskie w wielu przeglądarkach na Windows.
  • Walidacja HTML pomaga wykrywać błędy kodu HTML.
  • Walidacja CSS pomaga wykrywać błędy arkusza stylów.
  • Walidator HTML jest dostępny pod adresem validator.w3.org/nu/.
  • Walidator CSS jest dostępny pod adresem jigsaw.w3.org/css-validator/.
  • Stronę lokalną można walidować przez przesłanie pliku lub wklejenie kodu.
  • Błędy 404 mogą wskazywać na nieprawidłowe adresy zasobów.
  • Walidacja nie zastępuje testów funkcjonalnych.
  • Testowanie dostępności obejmuje m.in. obsługę klawiaturą i czytelność.
  • Wydajność witryny zależy m.in. od rozmiaru pobieranych zasobów.
  • Scenariusz testowy określa warunki, działanie i oczekiwany wynik.
  • Raport błędów dokumentuje wykryte problemy.
  • Po poprawieniu błędu należy powtórzyć test.
  • Witrynę warto sprawdzić również na rzeczywistym urządzeniu mobilnym.

📝 Zadania praktyczne

Projekt: „Testowanie i poprawianie witryny internetowej”.

Cel: sprawdzenie strony w różnych przeglądarkach i szerokościach ekranu, wykrycie błędów HTML i CSS oraz przygotowanie raportu testów.

📌 Przygotowanie projektu

Wykorzystaj własną witrynę utworzoną na wcześniejszych zajęciach z HTML i CSS.

Skopiuj jej pliki do folderu PSI_39.

Wszystkie testy i poprawki wykonujesz na jednej witrynie.

Jeśli witryna zawiera obrazy, zachowaj ich oryginalną strukturę folderów.

Zadanie 1 – Testowanie w przeglądarkach

  1. Otwórz plik index.html w Google Chrome.
  2. Sprawdź wygląd strony.
  3. Przetestuj menu i wszystkie odnośniki.
  4. Otwórz tę samą witrynę w Firefox lub Edge.
  5. Porównaj wygląd nagłówka, menu, kart i stopki.
  6. Sprawdź, czy obrazy wczytują się poprawnie.
  7. Zapisz wyniki porównania w pliku raport.txt.

Zadanie 2 – Testowanie responsywności

  1. Otwórz narzędzia deweloperskie.
  2. Włącz tryb Responsive.
  3. Ustaw szerokość 375 px.
  4. Sprawdź, czy strona nie wymaga niepotrzebnego przewijania poziomego.
  5. Ustaw szerokość 768 px.
  6. Sprawdź układ menu i elementów strony.
  7. Ustaw szerokość 1366 px.
  8. Sprawdź wygląd strony na dużym ekranie.
  9. Wykonaj zrzuty ekranu dla wszystkich trzech szerokości.
  10. Zapisz je jako mobile.png, tablet.png i desktop.png.

Zadanie 3 – Walidacja HTML

  1. Otwórz walidator HTML.
  2. Prześlij plik index.html lub wklej jego kod.
  3. Uruchom walidację.
  4. Przeanalizuj wykryte błędy.
  5. Popraw kod HTML.
  6. Powtórz walidację.
  7. Zapisz wynik w raporcie.
  8. Wykonaj zrzut ekranu wyniku walidacji jako walidacja-html.png.

Zadanie 4 – Walidacja CSS

  1. Otwórz walidator CSS.
  2. Prześlij plik style.css lub wklej jego zawartość.
  3. Uruchom sprawdzanie.
  4. Przeczytaj komunikaty walidatora.
  5. Popraw wykryte błędy składni.
  6. Powtórz walidację.
  7. Zapisz wynik w raporcie.
  8. Wykonaj zrzut ekranu jako walidacja-css.png.

Zadanie 5 – Testowanie funkcjonalności i dostępności

  1. Sprawdź działanie wszystkich odnośników.
  2. Sprawdź, czy obrazy są poprawnie wczytywane.
  3. Otwórz konsolę przeglądarki.
  4. Sprawdź, czy występują błędy związane z zasobami strony.
  5. Spróbuj obsługiwać stronę za pomocą klawisza Tab.
  6. Sprawdź, czy aktywny element jest widoczny.
  7. Sprawdź opisy alternatywne obrazów.
  8. Powiększ stronę do 200% i sprawdź jej czytelność.
  9. Zapisz wyniki testów w raporcie.

Zadanie 6 – Poprawki i raport końcowy

  1. Przejrzyj wszystkie wykryte problemy.
  2. Popraw błędy HTML i CSS.
  3. Usuń nieprawidłowe ścieżki do plików.
  4. Popraw elementy powodujące problemy z responsywnością.
  5. Sprawdź witrynę ponownie.
  6. Uzupełnij plik raport.txt.
  7. Wymień co najmniej trzy wykonane testy.
  8. Opisz wykryte błędy i sposób ich poprawienia. Jeśli błędów nie było, zapisz to w raporcie.
  9. Podaj końcowe wyniki walidacji HTML i CSS.
